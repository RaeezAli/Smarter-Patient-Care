## 1. Tech Stack (final)

| Layer | Tool |
|---|---|
| Language | Python 3.11+ |
| Web framework | Flask |
| Templates | Jinja2 (bundled with Flask) |
| Styling | Bootstrap 5 via CDN |
| Interactivity | Vanilla JS only if needed — no framework |
| Database | SQLite |

## 3. Setup Instructions

```bash
# 1. Clone and enter the repo
git clone <repo-url>
cd smarter-patient-care

# 2. Create and activate a virtual environment
python3 -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate

# 3. Install dependencies
pip install -r requirements.txt

# 4. Place raw MIMIC-IV Demo CSVs in data/raw/
#    (hosp/ and icu/ subfolders as downloaded from PhysioNet)

# 5. Build the database
python scripts/load_data.py
python scripts/build_indexes.py

# 6. Run the app
python run.py
# App will be available at http://127.0.0.1:5000
```

### `requirements.txt`
```
Flask>=3.0
pandas>=2.0
pytest>=8.0
```

Keep this list minimal. Do not add a dependency without a clear reason — every extra library is one more thing that can fail to install on someone's laptop mid-hackathon.

## 4. Git Workflow

- **Branch per person/feature**, merge to `main` frequently (at least every 2-3 hours) — with 4 people and 2 days, long-lived branches are a bigger risk than merge conflicts.
- Suggested branch names: `feature/timeline-backend`, `feature/qa-backend`, `feature/frontend-timeline`, `feature/frontend-qa`.
- Commit early and often. A commit that says "wip" is fine — this isn't a portfolio commit history, it's a working weekend.
- Whoever owns `db.py` and the dataclasses in `citations.py` should push those first — everyone else's code depends on those interfaces being stable.
- `.gitignore` must include: `venv/`, `data/raw/`, `data/mimic.db`, `__pycache__/`, `.env` — never commit raw patient-level data files or the generated DB, both for licensing reasons (PhysioNet terms) and repo size.

## 5. Coding Conventions

- **All SQL queries use parameterized placeholders** (`?`), never string formatting/f-strings with user input, even though this is a local hackathon demo — bad habits under time pressure are how mistakes ship.
- **Every function that returns patient data returns a dataclass with citations attached**, never a bare dict or raw tuple, per `citations.py`. If you're tempted to skip attaching a citation "just for now," don't — retrofitting citations later is more work than building them in from the start.
- **No bare `except:` blocks.** Catch specific exceptions (`sqlite3.Error`, `KeyError`, etc.) so failures are debuggable, not swallowed.
- **Type hints on all function signatures** in `app/` — this is a small codebase and type hints cost almost nothing but make it much faster for teammates (and the coding agent) to understand what a function expects and returns without reading its body.
- **Docstrings on every function in `timeline.py` and `queries.py`** — one line describing what it does and which tables it touches, since these are the functions most likely to be extended during the hackathon.

## 6. Testing Strategy

Given the time budget, testing should be targeted, not exhaustive:

- `test_timeline.py`: run `get_patient_timeline()` against 2-3 known patients (your "hero patients") and assert the returned events are correctly time-sorted and every event has at least one citation.
- `test_queries.py`: for each question in `QUESTION_REGISTRY`, test both a "data exists" case and a "no data / insufficient evidence" case. The insufficient-evidence path is the one most likely to be forgotten if untested — do not skip this.
- `test_citations.py`: assert that `TimelineEvent` and `QueryResult` cannot be constructed without a `citations` field being present (even if empty for the insufficient-evidence case) — this locks in the core safety guarantee of the whole project.

Run tests with:
```bash
pytest tests/
```

Run this before every merge to `main`, not just once at the end.

## 7. Two-Day Roadmap

### Saturday AM — Understand the data
- Load MIMIC-IV Demo into SQLite (`load_data.py`).
- Whiteboard the join map (see `DATABASE.md` Section 3).
- Pick 2-3 "hero patients" with rich data (multiple admissions, ICU stay, several labs/meds) to develop and demo against.
- **Checkpoint:** everyone can run one query and get a sensible joined result for a hero patient.

### Saturday PM — Parallel build
**Workstream A (2 people) — Backend**
- Build `db.py`, `citations.py` dataclasses first (these are the shared contract).
- Build `timeline.py`: `get_patient_timeline()`.
- Build 2-3 functions in `queries.py` to prove the pattern works end to end.

**Workstream B (2 people) — Frontend**
- Build `base.html` with the persistent safety banner.
- Build `index.html` (patient picker) and `timeline.html` against dummy/fake data first — don't block on the backend.
- Integrate with real backend output as soon as `timeline.py` returns real data.

**Checkpoint by end of Saturday:** timeline view works end-to-end for a hero patient, safety banner visible on every page.

### Saturday Evening — Finish the Q&A feature
- Implement all 7 questions in `queries.py` (see `API.md` Section 3).
- Build `qa.html` with all three states (found / insufficient evidence / error) visually distinct.
- Wire up `/patient/<id>/ask` routes.
- **Checkpoint:** all 7 questions work for at least one hero patient, including at least one that correctly returns "insufficient evidence."

### Sunday AM — Break things on purpose
- Test against 2-3 *other* patients, not just the hero patients.
- Deliberately test edge cases: a patient with sparse data, a question with no supporting records, an invalid `subject_id` in the URL.
- Fix what breaks. Document what you can't fix in time — this becomes your "one honest failure case" for the pitch.

### Sunday Midday — Evaluation & docs
- Fill in `docs/evaluation_report.md`: sample 15-20 facts across 3+ patients, verify manually, report accuracy and the baseline comparison.
- Fill in `docs/safety_statement.md` using `PRD.md` Section 10 and `ARCHITECTURE.md` as source material.
- Update `README.md` (can be a trimmed version of `PRD.md` + `ARCHITECTURE.md`) with run instructions.

### Sunday PM — Rehearse
- One person owns the pitch: problem → live demo (timeline + Q&A on a hero patient) → the one honest failure case → limitations → done.
- Time it. Aim under 5 minutes. Do at least one full run-through before the actual judging.
